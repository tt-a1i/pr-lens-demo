# 外部大仓库 PR 的动态讲解场景分析

这次读取五个外部项目的真实历史 PR，获取变更文件清单、核心文件差异和必要源码，并固定共同基点与 head。没有克隆或全量扫描这些仓库；图形和分镜由 Agent 依据源码编排，指标按需调用 Arc 原生分析器。五例均已输出明暗动态 SVG 和关键帧。

## Tokio 的调度器重写

[Tokio #1657](https://github.com/tokio-rs/tokio/pull/1657) 修改 100 个文件。PR 同时涉及队列、同步协调和任务结构；本条讲解选择本地队列替换、溢出、窃取，以及 Worker 搜索与停泊。

先用架构图保持 Worker、本地队列、共享队列的逻辑身份，再将 Chase-Lev 队列替换为有界环形队列。接着表现满队列时约一半任务向共享队列迁移，以及其他 Worker 的批量窃取。最后进入生命周期，解释执行、搜索、停泊之间的关系。

这个案例检验的是同一个 PR 中的结构替换和并发状态如何配合。队列间的任务迁移可以演示流动；Worker 的状态选择需要条件和回环，普通模块依赖图不足以讲完。

源码还显示，搜索数量限制使用宽松的原子读取作为优化，不能写成严格并发硬上限；停泊集合在该提交中是 `Mutex<Vec<usize>>`，也不能只照抄 PR 描述中的容器名称。PR 的单次任务分配、JoinHandle 和完整性能结果未纳入这条分镜。

## Vue 的编译绑定与内联模板

[Vue #2532](https://github.com/vuejs/core/pull/2532) 修改 11 个文件。当前讲解聚焦绑定元数据怎样连接脚本与模板编译，以及普通绑定对象和新增内联 render 闭包这两种产物。ref sugar 的完整语法改造可以独立成另一条主线。

数据流图展示编译信息与产物，不把编译器之间的关系画成浏览器运行时请求。然后模拟进入 `processExpression` 内的 `prefix` 函数，说明 setup 值经 unref 读取，组件导入直接引用，普通模式继续使用前缀。

Arc 原生函数分析器测得：

| 函数 | 圈复杂度 | 最大嵌套 |
| --- | --- | --- |
| 外层 `processExpression` | 22 → 22 | 2 → 2 |
| 嵌套 `processExpression.<locals>.prefix` | 2 → 6 | 0 → 2 |

这说明指标绑定也需要精确到实际改变的函数。原生测量分别统计嵌套函数；只拿外层数值会遗漏这处局部分支变化。动态图把 2 → 6 附着于 `prefix`，不会用整文件或整个编译器的总数替代它。[本地测量记录](measurements/vue.json)

## Django 的 ASGI 与同步契约

[Django #11209](https://github.com/django/django/pull/11209) 修改 38 个文件。当时新增 ASGIHandler 和应用入口，既有视图链仍是同步的。源码中的同步 `get_response` 经 `sync_to_async` 交接，响应再返回 Handler 编码发送。

第一段使用时序图，让异步服务、Handler 与原有同步视图链处在同一个阅读顺序中。第二段切换流程图，演示 `async_unsafe` 对当前线程运行中事件循环的检查：误用时抛异常，同步环境保留原调用。

这里的重点是接入新协议时保留旧契约，并建立保护边界。不能从 ASGI 名称直接推断该 PR 已实现 async views。`asgiref.Local` 的跨模块替换属于相关架构背景，当前分镜没有逐文件铺开。

## vLLM 的分区计算与归并

[vLLM #1348](https://github.com/vllm-project/vllm/pull/1348) 修改 6 个文件。它没有把所有调用直接替换成 V2。Python 入口在单分区，或 `num_seqs × num_heads > 512` 时使用 V1，其余情况走 V2。

第一段用流程图明确两条路径。第二段用数据流图把序列维度的分区计算展开：每个分区对应 512 tokens，产出局部输出、最大值和指数和，再由 reduce 内核重新缩放、合并到原输出张量。图中的多个分区是结构示意，实际数量由输入决定。

这里需要表现数据拆分、局部统计和归并，而不只是对某个模块放大。V1/V2 分流保留在最后的源码细节中，避免让分区主线误导读者认为所有请求都使用 V2。没有复述作者的速度结论为本地测量，也没有运行 GPU 基准。

## Kubernetes 的 API 类型引入

[Kubernetes #14175](https://github.com/kubernetes/kubernetes/pull/14175) 修改 8 个文件，主要是初版 Ingress 内部与 v1 类型、类型注册、转换、DeepCopy 和字段文档。不能画成已加入控制器或已经转发 HTTP 流量。

先用架构图解释新类型怎样进入现有 Scheme 和生成代码链。再用原生类型图展示 `IngressSpec → IngressRule → IngressPath → IngressBackend` 的包含关系，逐步展开 Host、Paths、ServiceRef、端口和协议。类型关系保持为静态关系，不播放请求流动。

这类 PR 检验的是声明契约与运行行为能否明确区分。使用该历史提交中的 `ServiceRef` 等真实字段，不替换为后来版本的 Ingress 模型。

## 对展示范围的调整

主要展示用这五种外部场景，保留 Arc #1359 作为自身基线。作者结账 demo 用于同一输入的 PRLens 图片对照；原先的搬迁和模块循环小案例保留为辅助材料。

共同的探索问题是如何选主线、保持对象身份、协调不同结构、安排字幕和代码，以及决定哪些局部分析信息值得进入画面。现有图结构已经能承载这些场景，当前主要缺口是讲解规则与动态编排的收敛。

可内嵌导出已有本地实现；原生分析已有案例级接入。通用的分析结果适配、多结构讲解编译与自动化发布应分别描述当前状态，不能因为演示能播放就视为这些环节全部完成。
